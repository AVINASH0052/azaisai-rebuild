## The reframe

You caught a real gap. I'd cut admin to one read-only page, and that was right for the *analytics* routes and wrong for the *control* routes — without a limits editor, the only lever on a customer is a database console, and every intervention is an unlogged manual `UPDATE`. That's not an admin gap, it's an audit gap. So doc 14 opens by explicitly superseding that call.

**The core design decision: a policy engine, not a pile of toggles.**

The tempting build is columns on `workspaces` — `max_concurrent`, `can_use_premium`, `is_suspended`. Works for three weeks. Then limits need to vary by plan *and* by customer *and* globally during an incident, the checks are scattered across six call sites that disagree, and nobody can answer "why is this customer throttled?"

Instead, one resolved object per workspace per request:

```
PLATFORM_DEFAULTS ← plan_policies ← workspace_overrides ⊓ global_clamps
```

Two details doing the heavy lifting:

- **The last step is a clamp, not a merge.** During a provider incident you set a global ceiling of `concurrent = 2`. If that merged like the others, a customer with an override of 8 keeps their 8 and your incident control does nothing.
- **A `source` map on every field.** The admin UI shows *concurrency = 1, source: override, set by avinash, reason: "chargeback pending", expires in 4 days*. That's the whole reason to build it this way.

Full limits catalogue in §2 — 15 limits × 4 plans, including `spend.daily_cents` denominated in **our COGS, not credits**, because credits are what we sold and cents are what we pay.

## Three things worth flagging

**Platform admin is a separate authz plane** (§6, now also [ADR-013](docs/12-DECISIONS-RISKS.md)). Not a role on `workspace_members`. Every user owns their personal workspace, so if admin were a workspace role, the distance between "owner of my own workspace" and "operator of the platform" is one mistaken `WHERE` clause.

**Prompts are masked by default in admin views.** The original's About page promises "your generations are private." An admin panel that shows every prompt by default quietly breaks that. Revealing one is a distinct audited action.

**`/admin/workspaces?filter=over_limit` is a sales lead list, not an ops queue** — customers who want to spend more than their plan allows. Falls out of the limits engine for free.

## The cost, stated plainly

This adds ~75 min and pushes the nominal schedule to **H12.75 — over the window.** I put that in [11](docs/11-DELIVERY-PLAN.md) rather than hiding it, spent the H11–H12 buffer knowingly, and re-ranked the cut order: **admin Tier A now outranks prompt-enhance and Stripe.** A limits control plane demonstrates more engineering judgement in a five-minute walkthrough than an LLM rewrite button does.

Tier A ships (engine + enforcement + 3 screens + audit + 2 circuit breakers). Tier B is the job inspector and model toggles. Tier C is schema-only. §10 has the split.

One rule I added on the way through and propagated to the risk register: **the resolver fails open.** A bug in the limits system must never lock every customer out of the product — bad JSON in an override returns platform defaults and logs, it doesn't deny. The credit check and the env-var spend cap still hold, so failing open costs bounded money, not correctness.

## The decision

**Trunk-based. Direct commits to `main`. No squashing, no rebasing, no history rewriting.**

That's a deliberate inversion of normal practice, and of my own default — I don't usually commit to a default branch. The brief forces it:

> "Commit the logs as you go, interleaved with the code they produced... **The commit order shows the order you actually worked in.**"

That makes the commit graph a deliverable. Squash-merging PRs destroys precisely the signal being graded — it collapses the log/code interleaving and replaces "the order you worked in" with "the order you merged in." A branch-and-squash flow produces a tidier history that's *worse* at the one job this history has.

Supporting reasons: solo build, so PR gates buy nothing; and Vercel deploys `main`, which is what makes "deploy at H1, every commit deploys" work.

**Flagging it, since it overrides a safe default:** I'll be pushing to `main` throughout. If you'd rather I branch and merge `--no-ff` at each checkpoint, that preserves order too, just with a noisier graph — say so and I'll switch.

## The part that's easy to get wrong

The capture hook appends to **one file per session, continuously**. So:

> The same log file appears in many commits, growing each time. One log file does *not* map to one commit.

Which means the checkpoint command has to be `git add -A`, not selective staging. At checkpoint N the hook has *already* written the entries that produced that code, so staging the whole tree co-locates them for free. Selective staging is exactly how the logs drift out of sync and end up looking like the one-lump dump the brief warns against.

Two rules follow: never `checkout`/`restore`/`stash` anything under `.agent-logs/`, and if the tree needs resetting, reset source paths explicitly.

## Two details worth calling out

**Safety moves earlier, since there's no PR gate.** Pre-commit runs typecheck + lint + gitleaks on staged (<10s); pre-push runs unit tests (<30s); CI runs everything. Tests deliberately aren't in pre-commit — a 30-second wait per commit is how people start passing `--no-verify`, and a bypassed gate is worse than none. When `main` breaks: **fix forward**, never rewrite. `fix: worker lease expiry off by 1000×` is an honest entry in the record the brief wants.

**Abandoned spikes get pushed and left.** The one reason to branch is a spike that might not pan out. If it fails, push the branch anyway — the brief asks for dead ends to stay visible, and an abandoned branch is the cleanest possible record of one.

The pre-submission audit includes `git log --diff-filter=D -- .agent-logs/` returning empty, plus a reflog check for force-pushes. Together those make "the record is unedited" a *verifiable* claim rather than an assertion in a README — which is stronger than anything I could write.

Yes to all of it — one Vercel deployment, one landing page, one sign-in form, admins land on `/admin`. Written up as [docs/16-AUTH-AND-ROUTING.md](docs/16-AUTH-AND-ROUTING.md).

## Why this is the better design, not just the simpler one

A separate `/admin/login` *feels* more secure and generally isn't. It's a second auth surface — second rate limiter, second session handler, second place to get redirect validation wrong — and the weaker of the two implementations defines your security. It also advertises that an admin panel exists, and it tempts you into a separate admin-password table, which is worse than the passwordless flow the rest of the product already uses. The control is authorization, not a separate door. Stripe, Vercel and Linear all route by role after a single sign-in.

**Routing precedence:** `returnUrl` (validated) → `/admin` if in `platform_admins` → `/studio/video`.

## Three things that make or break this pattern

**1. The decision is server-side.** The `platform_admins` lookup happens in `/auth/callback`, not in a client component reading a flag. A client-side role check is a rendering hint, never a control.

**2. No admin oracle.** The sign-in form must behave *identically* for an admin email and an unknown one — same copy, same timing, same errors. Any observable difference turns the login form into an admin-email enumeration tool. So the role lookup happens after code verification, never in `send-otp`.

**3. Step-up MFA.** This is the one place I'd push back on the literal ask. Email OTP alone isn't enough for a platform operator — mailbox compromise is the most common takeover path, and it would hand someone the whole platform. So:

| Level | Reached by | Unlocks |
|---|---|---|
| `aal1` | email code | the product — studio, history, credits |
| `aal2` | email code + TOTP | `/admin/*` |

Admins sign in exactly like everyone else, then enter one authenticator code before admin unlocks. Their *user* surfaces still work at `aal1` — MFA gates admin, not the account. Supabase supports assurance levels natively, so this is cheap.

On "admin credentials" specifically: admins don't get passwords. A password path just for admin means storing passwords and running a second credential system. Email OTP + TOTP is strictly stronger.

## Two gaps I closed while writing it

**Bootstrapping** — only a superadmin can grant admin, and there is no superadmin. So `scripts/seed-admin.ts` reads `SEED_ADMIN_EMAIL`, runs once, and *refuses to run if any admin row already exists* so it can't be replayed to escalate. And there is no code path from signup to `platform_admins` — not a flag, not an invite code, not an email domain.

**Demo access for the reviewer** — they need to see the dashboard. The seed creates a demo admin at the **`support` (read-only)** tier: it can view workspaces and the limits editor but can't set overrides, suspend anyone, or adjust credits. If those credentials leak, the blast radius is reading a seeded dataset.

Also worth knowing: a non-admin hitting `/admin` gets a **404, not a 403** — a 403 confirms the route exists.

Delivery cost is ~35 min total, split across the auth slot and the admin slot. If it tightens, TOTP is the cuttable piece (degrades to email-OTP admin, documented as a known limitation); the routing and layered authz don't get cut.
